# M0: сквозной RAG с DeepSeek, чанкированием и версионированием документов

## 1. Цель

Создать локально запускаемый Java-сервис, который:

1. загружает синтетические документы и их новые версии;
2. делит версии документов на чанки с метаданными;
3. создаёт embeddings и сохраняет их в PostgreSQL с pgvector;
4. отвечает на вопросы через настоящий DeepSeek API, используя только актуальные версии документов;
5. сравнивает две явно указанные версии документа;
6. проверяет исходящие запросы и ответы модели, учитывает расход токенов и пишет аудит.

M0 должен быть сквозным вертикальным срезом. DeepSeek, чанкер, embeddings, хранение и векторный поиск — реальные, не заглушки. Более сложные механизмы защиты и расширенная ACL развиваются в следующих этапах.

## 2. Принятые решения

### 2.1. Технологии и запуск

- Java 21 LTS.
- Spring Boot 3.x.
- Maven.
- Spring JDBC для работы с PostgreSQL и явного SQL для pgvector.
- Flyway для версионирования схемы БД.
- Jackson для JSON и строгой валидации ответа модели.
- DJL и ONNX для embeddings.
- PostgreSQL с расширением pgvector — единственная векторная БД в M0; in-memory замена в основном приложении не используется.
- Основной запуск локальный, без Docker. Существующий PostgreSQL используется напрямую.
- `docker-compose.yml` в M0 не требуется.
- Параметры подключения к БД и DeepSeek задаются переменными среды; секреты не сохраняются в репозитории.
- В `application.properties` будут env-плейсхолдеры для URL, пользователя и пароля БД, ключа и настроек DeepSeek, лимитов и таймаутов.

### 2.2. Границы основного runtime

Основной запуск всегда использует:

- настоящий `DeepSeekLlmGateway`;
- реальный чанкер;
- реальный `EmbeddingService` на DJL/ONNX;
- PostgreSQL/pgvector.

Заглушки внешних сервисов не предоставляются как альтернативный runtime-режим. Изолированные тестовые реализации допустимы только в unit-тестах, где нельзя делать реальные сетевые вызовы. Они не являются заменой end-to-end проверки с DeepSeek.

### 2.3. Сквозной пайплайн чата

```text
POST /api/v1/chat
  → AuthN
  → InputGuard
  → EmbeddingService
  → Retrieval + tenant/ACL + фильтр актуальных версий
  → PromptBuilder
  → EgressGuard
  → DeepSeek /chat/completions
  → OutputGuard
  → строгая проверка JSON и citations
  → ответ + аудит
```

Каждый компонент имеет отдельный интерфейс и явный результат. Отказ или ошибка security-компонента не должны незаметно превращаться в разрешение.

### 2.4. AuthN, tenant и ACL в M0

- AuthN: один локальный API-ключ, соответствующий одному заранее сконфигурированному пользователю.
- Один tenant.
- Для обычного retrieval доступны только документы с `access_level = PUBLIC`.
- Фильтр tenant/ACL выполняется в SQL до `LIMIT top-k`.
- Запрещается молчаливая `allowAll`-реализация ACL.
- Полноценные роли, несколько tenant и дополнительные уровни доступа относятся к M1.

### 2.5. InputGuard в M0

- Проверка пустого запроса.
- Ограничение максимальной длины запроса.
- Возврат безопасной ошибки без внутренних деталей.
- Более сложная защита от prompt injection относится к следующим этапам; системная инструкция не считается достаточной защитой сама по себе.

## 3. Модель документов, версий и чанков

### 3.1. Инварианты версионирования

- `documentId` и стабильный `document_key` не меняются между версиями.
- Каждая новая версия создаёт отдельную неизменяемую запись `document_versions`.
- Чанки привязываются к `document_version_id`, а не только к документу.
- Обычный поиск использует только версию, указанную в `current_version_id`.
- Старые версии не перезаписываются и не смешиваются с актуальной в top-k.
- Новая версия и все её чанки/embeddings записываются в транзакции.
- `current_version_id` переключается только после успешного завершения ingestion новой версии.
- При ошибке текущей остаётся предыдущая полностью рабочая версия.
- Повторная загрузка той же версии с тем же `content_hash` идемпотентна.
- Совпадение `document_key + version_label` с другим содержимым — конфликт, а не молчаливая перезапись.

### 3.2. Минимальная модель данных

```text
documents
  id, tenant_id, document_key, title, current_version_id

document_versions
  id, document_id, revision, version_label, content_hash,
  access_level, metadata JSONB, created_at

chunks
  id, document_version_id, chunk_index, content, content_hash,
  start_offset, end_offset, metadata JSONB, embedding vector(N),
  tenant_id, access_level, created_at

llm_usage
  usage_date, reserved_tokens, used_tokens

audit_events
  id, request_id, event_type, prompt_hash, latency_ms,
  input_tokens, output_tokens, guard_verdicts JSONB, created_at
```

Окончательные constraints и индексы определяются при проектировании первой Flyway-миграции. Размерность `vector(N)` фиксируется после выбора embedding-модели.

### 3.3. Метаданные чанков

В JSONB допускаются прикладные атрибуты:

- тип документа;
- подразделение;
- язык;
- теги;
- путь к синтетическому источнику;
- диапазон исходных абзацев;
- `synthetic = true`;
- при необходимости идентификатор канарейки.

Поля, участвующие в безопасности, связях и ограничениях поиска, хранятся не только в JSONB:

- `tenant_id`;
- `access_level`;
- `document_version_id`;
- `chunk_index`;
- `content_hash`;
- границы фрагмента в исходной версии.

Секреты, включая синтетические, не помещаются в метаданные и аудит.

## 4. Задачи M0

### M0-01. Каркас приложения и контракты

Создать Spring Boot/Maven-проект, пакетную структуру, конфигурацию и основные интерфейсы:

- `ChatController`, DTO запроса/ответа, `RequestContext`, `RagPipeline`;
- `AuthN`, `InputGuard`, `EmbeddingService`, `DocumentChunker`;
- `RetrievalService`, `PromptBuilder`, `EgressGuard`, `OutputGuard`;
- `LlmGateway`, ingestion и audit-компоненты.

Также:

- единый безопасный формат ошибок с `request_id`;
- отсутствие сырых промптов, документов, ответов модели и секретов в ошибках и логах;
- env-плейсхолдеры в `application.properties`.

Критерий готовности: приложение собирается, конфигурация валидируется, основные контракты не требуют перестройки при подключении следующих задач.

### M0-02. PostgreSQL, pgvector и миграции

- Проверить доступ к локальному PostgreSQL и право создать расширение pgvector.
- Добавить Flyway-миграции для документов, версий, чанков, бюджета и аудита.
- Настроить Spring JDBC и сериализацию/чтение vector.
- Обеспечить ограничения целостности и идемпотентности ingestion.
- Векторный индекс для небольшого корпуса M0 не обязателен; HNSW можно добавить позже без изменения API retrieval.

Критерий готовности: миграции повторяемо применяются к пустой БД; CRUD и vector-запросы работают с реальным PostgreSQL.

### M0-03. Реальный чанкер

Первая версия детерминированная:

- нормализация переводов строк;
- разделение абзацев по пустой строке;
- ограничение максимального размера чанка;
- перекрытие соседних чанков;
- дополнительное деление слишком длинных абзацев по границам предложений, при необходимости — принудительно;
- сохранение исходных offsets, диапазона абзацев и порядкового номера чанка;
- конфигурационные `chunk-size` и `chunk-overlap`;
- стартовые значения в символах: 1200/200, подлежат проверке на корпусе.

Критерий готовности: unit-тесты покрывают пустой текст, границы чанков, перекрытие, длинный абзац и сохранение offsets. Потеря или дублирование текста, кроме заданного перекрытия, отсутствует.

### M0-04. EmbeddingService на DJL/ONNX

- Выбрать компактную multilingual ONNX-модель после проверки доступности весов, лицензии и качества русского языка.
- Загружать модель при старте.
- Реализовать `float[] embed(String text)`.
- Проверить стабильную размерность и нормализацию векторов.
- Ошибка загрузки модели не должна приводить к незаметному fallback на случайные embeddings.

Acceptance:

```text
similarity("пароль от Wi-Fi", "какой пароль у вайфая")
  >
similarity("пароль от Wi-Fi", "как оформить отпуск")
```

Численный порог устанавливается после измерения на выбранной модели, а не выбирается произвольно заранее.

### M0-05. Ingestion и синтетический корпус

- Реализовать локальный command-line ingestion по пути к каталогу; REST остаётся для чата и compare.
- Поддержать создание документа и добавление новой версии.
- Выполнять pipeline: документ → версия → чанки → embeddings → PostgreSQL.
- Обеспечить транзакционное переключение актуальной версии и идемпотентный повторный запуск.
- Подготовить 30–50 синтетических регламентов, политик и FAQ вымышленной компании.
- Использовать только сгенерированные look-alike секреты; реальные данные не добавлять.

Критерий готовности: корпус загружается без дубликатов; новая версия сохраняет старую; ошибка новой версии не повреждает текущую; метаданные доступны для последующего retrieval и аудита.

### M0-06. Retrieval по актуальным версиям

- Выполнить embedding вопроса.
- Получить cosine top-k среди чанков текущих версий.
- Применить tenant, ACL и необязательные фильтры метаданных в одном SQL до `LIMIT`.
- Вернуть в контекст содержимое, `chunk_id`, документ, версию и метаданные.
- Не использовать embeddings как доказательство отсутствия текстовых изменений.

Критерий готовности: результаты относятся только к текущим версиям; устаревшие и ACL-недоступные чанки не попадают в кандидаты; порядок и top-k соответствуют cosine distance.

### M0-07. Настоящий DeepSeekLlmGateway

Написать тонкий HTTP-клиент без готового DeepSeek SDK:

```java
interface LlmGateway {
    LlmResponse chat(List<Message> messages, RequestContext context);
}
```

- Ручной POST на `/chat/completions`.
- Модель по умолчанию `deepseek-chat`, настраиваемые base URL и `max_tokens`.
- Connect timeout около 5 секунд, read timeout около 120 секунд.
- API-ключ из `DEEPSEEK_API_KEY`, только в HTTP-заголовке.
- EgressGuard вызывается внутри gateway непосредственно перед отправкой, чтобы не было обходного пути.
- Retry с exponential backoff и jitter только для 429 и 5xx.
- Общий дневной бюджет токенов по UTC.
- Атомарное резервирование до запроса и сверка с фактическим `usage` после ответа.
- Retry и повторный запрос на исправление JSON также расходуют бюджет.
- При превышении бюджета запрос к провайдеру не отправляется.
- Аудит: `request_id`, хэш промпта, токены, latency и вердикты guard-компонентов.

Критерий готовности: основной runtime получает реальный ответ DeepSeek; таймауты, retry, fail по бюджету и аудит проверены; ключ не попадает в payload, логи и аудит.

### M0-08. EgressGuard v1

Проверять исходящие сообщения и сериализованное тело на:

- значение сконфигурированного API-ключа, случайно попавшее в текст;
- AWS access key вида `AKIA...`;
- JWT;
- PEM private key.

Политика fail-closed: срабатывание, ошибка сканера или невозможность сериализации запрещают отправку.

API-ключ добавляется в заголовок после сканирования тела. Заголовок авторизации не проверяется на собственный ключ, иначе каждый легитимный запрос был бы заблокирован.

Качественный синтетический секрет regex не отличает от реального и тоже должен блокироваться при реальном вызове DeepSeek. Для M0 это ожидаемый безопасный результат.

Критерий готовности: каждое срабатывание и каждая ошибка сканера предотвращают сетевой вызов; событие фиксируется без копирования найденного секрета.

### M0-09. Сборка промпта и генерация с цитатами

- Передавать retrieval-документы как недоверенные данные в `<document>`.
- В системной инструкции запретить выполнение инструкций из документов.
- Запросить строгий JSON с ответом и списком `chunk_id`.
- Валидировать схему Jackson.
- Разрешать citations только на чанки, реально переданные в этом запросе и прошедшие ACL.
- При невалидном JSON выполнить ровно один повторный запрос; затем вернуть безопасную ошибку.
- Повторный запрос проходит EgressGuard, бюджет и аудит заново.

Критерий готовности: реальный ответ DeepSeek преобразуется в типизированный результат; неизвестные, устаревшие и чужие `chunk_id` отклоняются.

### M0-10. OutputGuard v1

- Проверять структуру ответа и citations.
- Проверять канарейки.
- Обнаруживать чрезмерные дословные совпадения с retrieval-документами.
- Не возвращать внутренние ошибки, скрытый контекст или найденные секреты клиенту.

Критерий готовности: тесты подтверждают отказ на поддельных citations, канарейках и превышении настроенного verbatim-порога.

### M0-11. Сравнение версий документа

Отдельная операция:

```text
GET /api/v1/documents/{documentKey}/compare?from=1.0&to=2.0
```

Правила:

- обе версии проходят AuthN, tenant и ACL;
- сравниваются только явно указанные версии одного документа;
- основной результат — детерминированный текстовый diff добавлений, удалений и изменений;
- diff ссылается на чанки конкретных версий;
- embeddings не используются для доказательства отсутствия изменений;
- изменение одного слова или числа обязано обнаруживаться;
- опциональное объяснение DeepSeek получает только подготовленный diff;
- LLM-путь сравнения: ACL → diff → PromptBuilder → EgressGuard → DeepSeek → OutputGuard/citations → аудит;
- LLM не может сослаться на чанк вне переданного diff.

Критерий готовности: compare корректно показывает добавления, удаления и изменения; обычный RAG по-прежнему использует только текущую версию; чужие tenant/ACL-недоступные версии недоступны.

### M0-12. Сквозная проверка и безопасность

- Загрузить небольшой корпус, затем полный синтетический корпус.
- Выполнить реальный чат-запрос к DeepSeek и получить ответ с корректными citations.
- Проверить новую версию документа и compare.
- Проверить fail-closed EgressGuard без фактической отправки запрещённого payload.
- Проверить бюджет при параллельных запросах и повторных попытках.
- Проверить, что аудит не содержит сырых секретов, Authorization, промптов и документов.
- Отдельно документировать оставшиеся ограничения M0.

Критерий готовности: все acceptance-критерии выше выполнены на реальных DeepSeek, DJL/ONNX и PostgreSQL/pgvector, а ограничения явно зафиксированы.

## 6. Что не входит в M0

- Несколько tenant и полноценная ролевая модель.
- Продвинутая защита от prompt injection и полноценный red-team набор.
- Гарантированное распознавание реальных и синтетических секретов по regex.
- Оптимизация pgvector для большого корпуса.
- Продакшен-эксплуатация, высокая доступность и внешний deployment.
- Использование текстовой системной инструкции как единственной защиты от утечек.

## 7. Начальные параметры, требующие проверки при старте

Эти пункты не блокируют фиксацию плана, но должны быть подтверждены перед соответствующими задачами:

- версия локального PostgreSQL, наличие pgvector и право `CREATE EXTENSION`;
- конкретная multilingual ONNX-модель, размерность и лицензия;
- точные численные пороги similarity и verbatim после измерений;
- окончательный формат входных файлов и передачи `document_key`, `version_label` и метаданных ingestion;
- начальное значение общего дневного бюджета токенов DeepSeek.
